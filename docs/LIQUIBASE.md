# Liquibase in energy-smart-meter

Everything that used to be typed by hand in the SQL editor now has an owner. Nothing should be created by hand again.

## Who owns what

| Object | Owner | Where |
|---|---|---|
| Catalog `energy_dev` / `energy_qa` / `energy`, schemas `bronze silver gold audit security liquibase` | **Admin, once** | `scripts/bootstrap_environment.py` (CI is blocked from `CREATE CATALOG/SCHEMA` on purpose) |
| Secret scope `energy-secrets` | Admin, once per workspace | `databricks secrets create-scope energy-secrets` (a CLI command, not SQL) |
| Group membership of service principals | Account admin | UI / SCIM |
| Tables (structure) | **Liquibase** | baselines `2026.09/10.0xx-baseline-*` generated by `scripts/generate_baseline_changelogs.py`, later changes as new files |
| Volume `bronze.raw` | Liquibase | `2026.10.100` |
| Grants | Liquibase | `2026.10.110-112`, `161-162` |
| Mask / row-filter functions | Liquibase | `2026.10.120-121` |
| `region` column + backfill | Liquibase (idempotent) | `2026.10.130-133` |
| Applying masks and row filters | Liquibase | `2026.10.140`, `150` |
| Secure view | Liquibase | `2026.10.160` |
| Iceberg table properties | Liquibase | `2026.10.170` |
| Data (rows) | Pipeline code | `src/` (never creates or alters structure) |

Not turned into changesets because they are queries, not changes: `SHOW ...`, `DESCRIBE ...`, `SELECT ...`.
Dropped from your manual script because they were invalid: `create volume energy.silver;`, `create volume energy.gold;`
(no volume name) and `create table energy.audit.pipeline_lineage;` (no columns; the baseline generator covers that table).

## Numbering

- `2026.09.001` audit table, `2026.10.002 ... 099` baselines (generated), `2026.10.100+` security and platform objects.
- Files run in filename order. A changeset may only depend on lower numbers (tests check this).

## Fixes made while converting your manual SQL (review these)

1. **Grants were incomplete.** Engineers had `USE SCHEMA` only on bronze; HR and business users had a table grant but no
   `USE CATALOG` / `USE SCHEMA`. All added.
2. **Business users could bypass the masked view.** They were granted the base table `gold_revenue_summary`, where revenue is
   unmasked. They now get the view, and `162-revoke-...` removes the base-table grant. Delete that one file if you do not want
   to change prod access.
3. **Backfill only touches NULL rows** (`AND f.region IS NULL`), instead of rewriting every row.
4. `REORG TABLE ... PURGE` is written in the documented form `REORG TABLE ... APPLY (PURGE)`.
5. `delta.enableDeletionVectors = false` is quoted (`'false'`) like the other properties.

## MUST READ before deploying: masks apply to your own pipeline

Masks and row filters evaluate `is_account_group_member(...)` for whoever runs the query, including jobs.
`fact_consumption` joins on `dim_customer.LCLid`; for a principal outside `energy_data_engineer` that column reads `********`, the
join silently returns NULLs, and facts are written with NULL keys.

- Add **every** principal that runs jobs or Liquibase (the dev/qa/prod service principals, and you) to account group `energy_data_engineer`.
- Keep them OUT of `north_team` / `south_team`, otherwise the row filter hides rows from the pipeline.
- Verify with a job-run query: `SELECT is_account_group_member('energy_data_engineer')` must return `true`.

## Privileges the deploy principal needs

Setting masks, filters and grants requires ownership or `MANAGE` on the tables. Simplest: make the principal the catalog owner
(`ALTER CATALOG energy_dev OWNER TO \`<application-id>\``). For prod, existing tables are owned by whoever created them, so grant
`MANAGE` or transfer ownership before the first prod deploy, otherwise `140` and `150` fail. Also `CREATE VOLUME` on `bronze`,
`CREATE FUNCTION` on `security`. I could not verify these on your workspace, so the first dev deploy will show what is missing.

## Rolling this out safely

1. `dev`: run `bootstrap_environment.py` for `energy_dev`, merge, watch the deploy. Baselines create empty tables; the
   changesets then apply on top.
2. `qa`: same.
3. `prod` (`energy`): baselines are recorded as already applied (preconditions). The security changesets re-run, which is safe
   because every statement is idempotent (`CREATE OR REPLACE`, `SET MASK`, `SET ROW FILTER`, `GRANT`, `IF NOT EXISTS`).
   Exception: `162` revokes access and `170` re-runs `REORG ... PURGE` (rewrites the small `dim_tariff` table).
4. If Liquibase ever fails midway, fix forward with a NEW changeset. Never edit a merged one.

## Adding a change from now on

New column: `sql/ddl/changelogs/2026.MM.NNN-add-<col>-to-<table>.yml` (copy `2026.10.130`), numbered above everything existing.
`pytest tests/unit/test_changelogs.py` checks id = filename, `runInTransaction: false`, rollback present, only `${energy_catalog}`
used, and that the CI DDL guard would let it through.
